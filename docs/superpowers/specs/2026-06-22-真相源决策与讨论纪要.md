# 真相源决策与讨论纪要

日期：2026-06-22

状态：已达成结论，待落入 codex 设计文档（`2026-06-19-ai-static-cms-design.md`）

> 本文记录两版设计（codex 版 / Claude 版）的路线分歧、讨论过程与最终决策。核心是回答一个问题：**页面的"真相源"该是 HTML 还是结构化 blocks。**

---

## 1. 背景：两版设计的根本分歧只有一个

我们有两份设计文档：

- **codex 版**（本项目正在实现）：`docs/superpowers/specs/2026-06-19-ai-static-cms-design.md`
- **Claude 版**：`内容驱动建站系统-设计文档.md`

两份不是"详略不同的同一个设计"，而是**两条对立路线**，分歧点只有一个——**真相源（编辑态里、重新发布时依据谁）是谁**：

| | codex 版（正在实现） | Claude 版 |
|---|---|---|
| 真相源 | **HTML 草稿**（markdown/blocks 只是辅助元数据） | **blocks / schema**（HTML 是派生物） |
| AI 产出 | 直接吐成品 HTML | 只填 blocks（structured output） |
| 渲染 | 没有渲染器，AI 即渲染 | 目标态用确定性渲染器（代码）把 blocks 算成 HTML |

Claude 版 §8 的"B 胜 7/平 1/A 胜 0"实验里，**所谓"方法 A"指的就是 codex 这版**。也就是说 Claude 版本质是在论证"HTML 当真相源是错的"。所以这需要一次明确拍板，而不是把两份拼在一起。

---

## 2. 最关键的概念澄清：访问态 ≠ 真相态

讨论中最容易混淆的一点：**"真相源"说的不是访客访问的东西，而是后台编辑/重发布时依据的东西。**

| | 访问态（访客打开网页） | 真相态（后台改、重发布时依据谁） |
|---|---|---|
| codex 版 | 静态 HTML（S3/CDN 直出） | HTML |
| Claude 版 | **静态 HTML（S3/CDN 直出）** | blocks |

**两版访客拿到的都是预先生成好的静态 HTML 文件，体验完全一样。** blocks / schema 只躺在后台数据库里给编辑器用，**访客永远碰不到**。

所以"我希望访客直接访问 HTML，而不是访问时才转换"——这一点两版本来就都满足，不构成分歧。

---

## 3. "结构化数据 → HTML" 到底是不是 WordPress？

**不是。** 区别不在于有没有结构化数据，而在于这步转换**发生在什么时候**：

```
WordPress：  DB 结构化数据 → PHP 现场拼 → HTML    ← 每次访问、活服务器上跑
Claude 版：  blocks → 渲染 → HTML                ← 发布时跑一次，之后是死文件
codex 版：   AI → HTML                          ← 创建时跑一次，之后是死文件
```

界定 WordPress 的根本特征是**"每次访问都在活服务器上现拼 HTML"**——慢、要服务器、PHP/插件 CVE 全从这来。

而 Hugo、Astro、Next 的 SSG 也都是"结构化数据 → HTML"，没人说它们等于 WordPress——因为它们是**构建时转一次，之后服务静态文件**。

> 一句话：**"有结构化中间层" ≠ WordPress；"访问时现场渲染" = WordPress。**
> 只要转换是发布时一次性的、访客拿死文件，就已经和 WordPress 划清界限了，跟真相源是 HTML 还是 blocks 无关。

---

## 4. 两版的机制差别，到底差在哪

用户的理解（已确认正确）：

- 两边 S3 都是静态 HTML，访客体验一样。
- codex：真相 = HTML，改就是改 HTML。
- Claude：数据库存结构化数据 + 元信息（用了哪个模版、s3 key），改 → 回写结构化数据 → 再同步更新 S3 文件。

最关键的差别是**有没有"重新渲染"这个动作**：

```
codex：  存的 HTML  ──(只包一层外壳)──▶  S3 的 HTML
         改 = 直接改这份 HTML。全程没有"重新算一遍"这一步。

Claude： 结构化数据  ──(渲染器=代码，算一遍)──▶  S3 的 HTML
         改 = 改结构化数据，再让渲染器重新算一遍，覆盖 S3。
```

- codex 的 HTML **本身就是成品**，不存在"由谁算出来"。
- Claude 的 HTML **每次发布都是被渲染器现算出来的**，数据 → HTML 是一个确定的函数。

---

## 5. blocks 到底好在哪？——只在两件事上，且都不是"编辑"

### 5.1 核心一句话

> **HTML 把"内容"和"长相"焊在一起、复制了 N 份存着；blocks 只存内容一份、长相只存一份。**

具体对比（以参数表 spec-table 为例）：

**HTML 为真相**——每个产品页文件里都躺着这么一坨，且在 300 个页面里复制了 300 份：

```html
<table class="spec-table" style="border:1px solid #888; background:#f5f5f5">
  <tr><td>检测速度</td><td>1200件/分钟</td></tr>
</table>
```

灰色和"检测速度/1200"焊在同一文件里。

**blocks 为真相**——每页只存数据，一个颜色、一个 `<table>` 都没有：

```json
{ "type": "spec", "rows": [{ "k": "检测速度", "v": "1200件/分钟" }] }
```

灰色长什么样只写在唯一一处（spec 模板）。

### 5.2 因此 blocks 只在这两件事上更优（且都是"重新生成"，不是"编辑"）

1. **全站换皮 / 改结构**（灰改蓝、表格改卡片）：
   - HTML 为真相 → 300 个文件各有一份拷贝，且 AI 当初一页页自由写、300 份压根不一样，连全局替换都不敢用 → 只能重跑 AI（漂移）或写脆弱的 HTML 改写器。
   - blocks 为真相 → 改一处模板，渲染器把 300 份数据重算一遍，全站一致，内容一字未动。

2. **多语言增量**：
   - HTML 为真相 → 中文焊在标签里，改一句也得整页重翻，可能漂移、可能翻坏标签。
   - blocks 为真相 → 每个文本字段带稳定 ID + hash，改一句只重译那一句，标签从不进翻译器。

### 5.3 一个重要澄清：日常改文字图片，两边一样简单

如果"改"永远只是改文字/图片/链接（不动结构、不动版式），每个能点的文字背后就对应一个字段，回写毫不困难——**codex 和 Claude 一样简单，不构成差别**。

> 所以"blocks 双向编辑更难建"这个说法，对"只改内容"的场景并不成立。
> blocks 的成本只在 5.2 那两件**重新生成**的事上才换回价值。

---

## 6. 本项目的决策前提

用户对本站（DGCRANE 起重机站）的两个关键判断：

1. **上线后不全站换皮 / 不改结构**（"应该不改变外观了都"）。
2. 日常只改文字图片。

→ 5.2 的第 1 个杀手锏用不上；5.3 说明日常编辑两边一样。
→ **blocks 渲染器 + 结构化存储 + 双向编辑器的前期税，交了也回不了本。**

---

## 7. 最终决策

### 7.1 结论：先走 codex 那套（HTML 当真相源），blocks 方案保留为未来选项

**两个方案都保留，先走 codex。** 当前不建 blocks 渲染器——为一个本阶段不会用到的能力背一套要长期维护的地基，是亏的；HTML 当真相源对本站更简单、AI 自由度也更高。

blocks 方案不废弃，作为未来选项保留：一旦后续真的出现频繁全站换皮/改结构的需求，可凭 §7.2 的标记把 HTML 反解析回结构、再切到渲染器，迁移成本可控。**保留它的唯一前提，就是从第一天起把 §7.2 的标记带全。**

### 7.2 唯一保险：多语言——用"标记"而非"渲染器"拿到字段级增量

多语言是 blocks 剩下的唯一真优势。但**不用建整套 blocks 也能拿到大半**，关键只有一点：

> **让 AI 出的 HTML 里强制带上稳定标记**：`data-template`、`data-field`，再给每个区块一个稳定的 `data-block-id`。

codex 设计本来就有 `data-template` 和 `data-field`（见 `2026-06-19-ai-static-cms-design.md` §4.1），只需再补一个稳定的 `data-block-id`。这样将来做英文站时，可以**直接在 HTML 上按字段比对**，哪个 `data-field` 的文字变了就只重译那个，不用整页重翻，也不用建渲染器。

### 7.3 最终架构（中间路线，非"非 A 即 B"）

```
真相源 = HTML（codex）
  + HTML 里强制带 data-template / data-field / data-block-id 标记
  → 改文字图片：直接改，简单
  → 不换皮：本来就不需要渲染器
  → 将来要英文站：靠这些标记做字段级增量翻译，不用建 blocks
```

一句话：**HTML 当真相源 + 标记不能省。标记是几乎零成本的保险，渲染器才是那笔不该交的税。**
