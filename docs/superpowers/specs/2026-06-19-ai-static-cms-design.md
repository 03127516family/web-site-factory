## 1. 背景

现有网站基于 WordPress，技术和内容管理方式已经不能满足后续需求。目标不是简单更换一个 Headless CMS，而是建立一套“内容驱动页面表达”的网站生产系统：运营人员提供 Markdown、旧站内容或产品资料，AI 根据内容和可用模板生成最终 HTML，人工可视化审核后发布为静态网站。

本设计先替换一个网站，保留以后扩展多站点的可能，但首期不实现多站管理。

## 2. 目标

系统需要实现以下核心闭环：

```text
建立参考页面和模板库
-> 输入 Markdown 或旧站内容
-> 手动、半自动或自动选择生成策略
-> AI 生成完整 HTML 草稿
-> 系统校验
-> 人工可视化审核和修改
-> 保存版本
-> 发布到 S3/CDN
-> 动态模块通过 API 加载数据
```

首期以运营人员使用为主，同时保留技术人员通过 Markdown 和版本记录介入的能力。

## 3. 核心原则

### 3.1 内容驱动页面

模板不是要求内容填写的固定表单。Markdown 也不需要预先提供 `headline`、`features`、`faq` 等固定字段。

系统先理解内容，再判断适合使用哪些页面表达方式。内容中没有 FAQ，就不生成 FAQ；没有参数，就不强行生成参数表。

### 3.2 AI 直接生成最终 HTML

首次创建页面时，AI 生成一份完整的页面内容 HTML 草稿，而不是只生成 JSON，再由另一套组件系统重建内容。发布器只负责加上稳定的文档外壳、全局 CSS/JS 和 SEO head，不重新解释或改写 AI 生成的页面内容。

后续修改默认只重写选中的 section 或可编辑内容，避免整页重新生成造成无关变化。需要大改版时，可以重新编排整页，但必须产生新草稿并重新审核。

### 3.3 HTML-first，但不是无约束 HTML

HTML 是页面的主要编辑和审核对象。系统同时保存原始 Markdown、模板使用信息、SEO 元数据、版本和发布记录，以支持追溯、局部编辑、多语言、回滚和重新发布。

AI 生成的 HTML 必须使用允许的模板或受控兜底结构，并通过结构和安全校验，不能自由插入脚本、未知动态模块或危险属性。普通模板默认不允许脚本；只有系统白名单中的动态 Runtime 可以执行脚本。

### 3.4 静态主体，动态模块统一走 API

页面主体发布为静态 HTML。相关产品、产品列表、表单和 AI Bot 等动态模块统一通过 API 获取数据，首期不做发布时动态数据注入。

### 3.5 草稿与线上发布隔离

所有编辑先进入 PostgreSQL 草稿和版本记录。S3 只保存已经发布的静态文件。保存草稿不会影响线上页面。

### 3.6 真相源决策（HTML 优先，blocks 方案保留）

> 决策日期：2026-06-22。完整讨论见 `2026-06-22-真相源决策与讨论纪要.md`。

存在另一条对立路线（记为 **blocks 方案**）：真相源不是 HTML，而是结构化 blocks/schema，发布时由确定性渲染器（代码）把 blocks 算成 HTML。两条路线访客侧完全一样（都是 S3/CDN 直出的静态 HTML），分歧只在后台真相源是谁。

**本项目决策：先走本方案（HTML 当真相源），blocks 方案作为未来选项保留，不现在实现。**

理由：

- blocks 方案的收益只在两件 **"重新生成"** 的事上才回本——**全站换皮/改结构** 与 **多语言整页重译**。日常只改文字/图片时，两套一样简单。
- 本站上线后预计不全站换皮、不改结构，因此 blocks 渲染器 + 结构化存储 + 双向编辑器属于交了回不了本的前期税。
- HTML 当真相源更简单、AI 自由度更高、链路更短，适合当前阶段。

**保留 blocks 方案的钩子（关键，不能省）：** 强制 AI 产出的 HTML 携带稳定标记 `data-template` / `data-field` / `data-block-id`（见 §4.1）。这样：

- 将来要英文站时，可直接在 HTML 上按字段比对，只重译变化的 `data-field`，拿到字段级增量翻译，**无需建渲染器**。
- 万一未来需要切到 blocks 方案，这些标记是把 HTML 反解析回结构的现成抓手，迁移成本可控。

一句话：**HTML 当真相源 + 标记不能省。标记是几乎零成本的保险，渲染器才是当前不该交的税。**

## 4. 模板库的含义

模板库不是把每个页面完整拆成一组固定组件，也不是要求所有页面拥有相同结构。

建设模板库时，先选择首页、产品详情页、解决方案页、文章页、案例页和联系页等代表性页面，形成页面风格和布局参考。再从这些页面中沉淀经常重复、适合受控编辑的 HTML 表达形式，例如首屏介绍、图文内容、优势列表、参数表、FAQ 和 CTA。

页面本身没有固定区块清单。AI 可以根据内容自由组合已有表达形式。特殊内容可以使用普通富文本或 Raw HTML 兜底，不要求所有元素都组件化。

### 4.1 模板标记

模板生成的 section 使用以下标记：

```html
<section data-template="hero-basic@1" data-block-id="b_3f9a" class="hero hero-basic">
  <h1 data-field="headline">工业级视觉检测系统</h1>
  <p data-field="subtitle">适用于高速产线。</p>
</section>
```

`data-template="hero-basic@1"` 表示模板 ID 为 `hero-basic`，模板版本为 1。它不是页面中的模板序号。

`data-block-id="b_3f9a"` 是该区块在页面内的**稳定唯一标识**，生成时分配、之后不随内容或顺序改变而变。它是多语言字段级增量翻译和未来可能切换 blocks 方案的抓手（见 §3.6），即使首期不做多语言也必须从一开始就带上。同一页内不得重复；调整顺序、增删区块时已有区块的 id 保持不变。

`data-field="headline"` 表示这是模板内可识别、可编辑的内容点。字段由各自模板定义，不是所有模板都必须拥有 headline，也不要求 Markdown 按字段提供内容。多语言增量比对以 `(data-block-id, data-field)` 为键，对其文本算 hash，只重译 hash 变化的字段。

### 4.2 模板版本

已发布模板不可原地改变结构。结构变化时发布新版本，例如 `hero-basic@2`。旧页面继续按旧版本校验和编辑，除非执行明确的迁移操作。

### 4.3 模板契约预留

首期预留模板契约概念，不构建复杂的在线模板管理器。最小契约包括：

- 模板 ID 和版本
- 模板 HTML 或结构参考
- AI 使用说明和示例
- 允许的 `data-field`
- 是否允许重复
- 是否允许脚本、iframe 或内联样式

后续可扩展字段类型、长度限制、位置规则、SEO 规则和动态模块协议。

首期模板由项目代码或受控配置维护。运营人员能够选择和使用模板，但不能在线修改模板 HTML。

## 5. 内容输入与生成模式

### 5.1 输入来源

系统接受：

- 完整长文 Markdown
- 带明确标题、列表、表格和 FAQ 层级的 Markdown
- 产品资料和文章资料
- 从 WordPress 页面提取并清理后的 Markdown 或 HTML

解析器先识别标题、段落、列表、表格、图片和链接等确定结构，AI 再补充语义判断。

### 5.2 生成模式

系统提供三种模式：

1. 自动模式：AI 判断页面类型、模板组合、区块顺序和动态模块。
2. 半自动模式：用户指定页面类型、必须包含或禁止包含的内容及风格，AI 完成其余编排。此模式作为日常默认模式。
3. 手动模式：用户指定模板或页面大纲，AI 负责使用内容生成最终 HTML；内容不足时必须提示，而不是编造关键事实。

无论哪种模式，内容仍然是页面生成的依据。手动指定模板只是增加约束，不要求 Markdown 变成固定字段表单。

### 5.3 AI 输出

首次生成输出完整的页面内容 HTML 草稿，包括：

- 页面主体结构
- 使用的模板标记
- 可编辑内容标记
- 动态模块占位
- 与页面内容对应的 SEO 草稿

AI 不直接发布页面。生成结果必须进入校验和人工审核。

## 6. HTML 校验

系统使用 HTML Parser 和 Sanitizer 校验生成及编辑后的 HTML，而不是只做截图检查。

校验分为：

- 模板合法性：模板 ID、版本和启用状态存在。
- 结构合法性：关键 `data-template`、`data-block-id` 和 `data-field` 未被删除，模板边界没有明显破坏；`data-block-id` 在页面内唯一、不缺失。
- 内容合法性：关键内容非空，链接、图片和标题层级合理。
- 安全合法性：禁止未知脚本、事件属性、`javascript:` 链接和非白名单 iframe。
- 动态模块合法性：模块类型和参数符合系统协议。
- 页面基础检查：slug、H1、SEO 标题、描述和图片 alt 等。

校验结果分为：

- 错误：禁止发布。
- 警告：允许审核人员决定是否发布。
- 通过：可以进入发布流程。

首期可以采用较宽松的结构校验，仅强制关键标记和安全规则；模板契约完善后逐步提高严格度。

## 7. 可视化审核与编辑

后台编辑器将草稿 HTML 加载到隔离 iframe 中，并使用与正式网站相同的 CSS。编辑器 UI 和正式页面样式不能互相污染。

运营人员可以：

- 点击 `data-field` 修改文字、图片和链接
- 删除、复制和调整 section 顺序
- 更换合适的同类模板
- 要求 AI 重写当前 section
- 根据补充内容生成新 section
- 在电脑、平板和手机尺寸下预览
- 必要时重新编排整页并生成新草稿

普通运营人员不能任意修改 DOM、脚本和全局 CSS，也不能删除系统关键标记。首期不开放整页源码编辑。

保存时，系统删除编辑器辅助元素，清理危险 HTML，重新校验，并把结果保存为新的草稿版本。保存草稿不修改 S3。

## 8. 动态数据

首期所有动态数据统一走 API，不做发布时静态注入。

普通静态内容由 AI 直接写入 HTML。动态内容由 AI 生成受控占位，例如：

```html
<section
  data-template="related-products@1"
  data-dynamic="related-products"
  data-category="vision"
  data-limit="4"
>
  <h2 data-field="title">相关产品</h2>
  <div data-slot="items"></div>
</section>
```

页面公共 JavaScript Runtime 扫描 `data-dynamic`，请求对应 API，并将返回数据渲染到 `data-slot`。

首期动态模块包括：

- 相关产品
- 产品列表
- 联系/询盘表单
- AI Bot 或商务通入口

每类动态模块需要定义允许的参数、API 响应结构、加载状态、空状态和失败降级。API 失败不能影响静态页面主体访问。

## 9. 存储与系统组件

### 9.1 PostgreSQL

PostgreSQL 是后台管理数据库，保存：

- 原始 Markdown
- 当前 HTML 草稿
- 页面版本
- 模板使用信息
- slug 和 SEO 元数据
- 多语言关系
- 用户、权限和操作日志
- 发布状态与任务记录
- 产品、文章、分类和表单等动态 API 所需的结构化业务数据

### 9.2 S3/CDN

S3 不是后台数据库。对象存储按不同 bucket 或路径分为两类：

- CMS 媒体资源：运营上传的图片、附件及优化后的资源。
- 网站发布产物：已经发布的 HTML、CSS、JavaScript、图片副本和站点文件。

网站发布产物示例：

```text
/index.html
/products/a/index.html
/assets/*
/app.css
/app.js
/sitemap.xml
```

CDN 位于 S3 前面，为访问者提供缓存和分发。

### 9.3 后台服务

后台服务连接 PostgreSQL 和 S3，承担：

- 内容和版本 API
- AI 生成编排
- HTML 校验和清理
- 预览
- 发布任务
- 动态数据 API
- 权限和审计

数据库与 S3 不直接互连，由后台服务和发布 Worker 通过数据库驱动及 S3 SDK 协调。

### 9.4 预留的 Lambda 发布时组合方案

最终发布架构预留使用 Lambda 或等价发布 Worker 统一管理 Header 和 Footer，但不在用户访问时实时渲染页面。

源码和发布产物分开保存：

```text
/source/fragments/header.html
/source/fragments/footer.html
/source/pages/products/a/body.html
/source/pages/products/a/meta.json

/releases/v1/products/a/index.html
/releases/v2/products/a/index.html
```

发布任务执行以下流程：

```text
Header
+ 页面 Body
+ Footer
+ 页面 SEO 元数据
-> Lambda/发布 Worker 组合完整 HTML
-> 写入新的 S3 Release
-> 完整校验
-> CloudFront 切换或刷新到新 Release
```

Header 或 Footer 在源码层只维护一份。修改后由发布任务自动批量生成受影响页面，不需要人工逐页修改。用户访问时仍然由 CloudFront/S3 返回已经生成好的完整 HTML，不依赖 Lambda 在线运行。

发布失败时继续使用旧 Release。回滚通过重新指向上一个完整 Release 完成，不能让半成品页面进入正式路径。

该方案目前作为目标架构记录，首个页面模板原型不实现 Lambda、S3 Release 切换或 CloudFront 自动刷新。原型阶段假设 Header/Footer 组合能力已经存在，重点验证页面主体模板。

#### 原型阶段的 Header/Footer 模拟

iframe 可以用于非常早期的视觉占位，但不能作为正式实现或最终验收方式，原因包括：

- iframe 内外不属于同一个 DOM。
- CSS、字体和响应式上下文相互隔离。
- 高度和移动端导航需要额外通信。
- 搜索引擎看到的结构与 Lambda 最终返回的完整 HTML 不一致。

如果只是暂时集中开发产品页主体，可以把 Header/Footer 放入 iframe，并明确它们是可丢弃占位。更接近 Lambda 结果的开发态模拟方式，是通过本地 fragment loader 把独立 Header/Footer 注入同一个 DOM；最终结构验收必须使用扁平化后的完整 HTML。

### 9.5 搜索

搜索不进入首期范围。后续可以从已发布 HTML 和元数据构建独立搜索索引。搜索索引始终是派生产物，不是页面源数据。

## 11. 发布与回滚

发布时冻结当前草稿为不可修改版本。发布 Worker 完成：

1. 读取冻结版本。
2. 给页面内容 HTML 包装稳定的文档外壳，并注入站点 head、SEO、全局 CSS/JS 和动态 Runtime；不重新生成页面内容。
3. 执行最终安全校验。
4. 生成完整 HTML 文件。
5. 上传临时 release 路径。
6. 校验文件存在、hash 和关键资源引用。
7. 更新正式 S3 路径并刷新 CDN。
8. 成功后更新数据库的发布版本和状态。

任一步骤失败时，旧版正式文件和 `published_version_id` 保持不变。

回滚不是只修改数据库指针，而是把历史版本重新执行一次发布任务，恢复 S3 文件并刷新 CDN。

## 12. WordPress 迁移

迁移分批执行：

1. 盘点页面、文章、产品、分类、媒体、URL、SEO、插件功能和多语言关系。
2. 优先通过 WordPress API、数据库或导出文件提取内容；无法取得权限时再抓取公开 HTML。
3. 清理主题导航、页脚、脚本和无关 DOM，转换为 Markdown 或标准内容，同时保存原始 HTML。
4. AI 根据内容和模板库生成新 HTML 草稿。
5. 检查正文、图片、链接、表格、标题层级、SEO、动态模块和移动端效果。
6. 尽量保持原 URL；必须改变时建立 301 映射。
7. 按普通文章、产品页、核心落地页和首页分批切换。

旧页面无法可靠重构时，可以使用 Raw HTML 兜底，先保证访问和 URL 稳定，再逐步转为受控页面。

## 13. 多语言

多语言是后续阶段能力，不进入首个 MVP，但数据模型、模板标记和动态 API 从首期开始避免阻断它。

每种语言保存和发布独立静态 HTML，例如：

```text
/zh/products/a/index.html
/en/products/a/index.html
```

目标语言页面默认保持源页面模板 ID、区块顺序和关键标记（含 `data-block-id`），只翻译和调整内容。语言长度或文化表达需要不同布局时，可以人工更换模板。

源页面更新后，系统以 `(data-block-id, data-field)` 为键、对源文本算 hash 做差异比对，**只重译 hash 变化的字段**，不整页重翻，也不自动覆盖目标语言线上版本。调整顺序或增删区块靠 `data-block-id` 识别，不误判全变。每种语言都必须单独审核和发布。被人工复核过的字段，源字段未变时不被机翻覆盖；源字段一变标记过期再重译。

动态 API 接收 locale 参数。每种语言独立管理 slug、SEO、canonical、hreflang 和 sitemap 信息。

## 14. 权限与审核边界

首期提供最小角色：

- 编辑者：创建页面、修改草稿、调用 AI、发起审核。
- 发布者：审核、发布和回滚。
- 管理员：管理用户、全局配置，以及通过受控发布流程注册的模板版本和启用状态；首期不能在线编辑模板 HTML。

所有生成、编辑、校验、发布和回滚操作写入审计日志。AI 永远只生成草稿，不能绕过人工审核直接上线。

## 15. 错误处理

- AI 超时或输出不合法：保留输入和上一个草稿，允许重试，不覆盖可用版本。
- HTML 校验失败：展示具体 section 和错误原因，禁止发布。
- 动态 API 失败：显示空状态、隐藏模块或展示预设降级内容，静态主体继续工作。
- S3 上传失败：发布任务失败，线上旧版不变。
- CDN 刷新失败：保留发布记录并重试，后台明确显示 CDN 状态。
- 数据库与 S3 对账异常：通过版本号、S3 key 和 HTML hash 发现并提供重新发布能力。

## 17. MVP 范围和实施顺序

实施优先级按照页面生产链路，而不是先建设庞大的后台：

1. 选择少量代表性页面，确定站点视觉规范和页面表达范围。
2. 建立第一版受控模板库和模板标记规则。
3. 实现 Markdown 输入和基础解析。
4. 实现自动、半自动和手动生成模式。
5. 让 AI 生成完整 HTML 草稿，并实现最小 HTML 校验。
6. 实现可视化审核、字段修改、section 排序和局部 AI 重写。
7. 实现 PostgreSQL 草稿、版本和最小页面管理。
8. 实现发布 Worker、S3/CDN 发布和回滚。
9. 实现相关产品、产品列表、表单和 AI Bot 动态 API。
10. 选择少量 WordPress 页面完成迁移验证。

首期不包含：

- 在线模板 HTML 编辑器
- OpenSearch
- 完整多语言生成和变更同步
- 多站点管理
- 复杂审批流
- A/B 测试和个性化推荐
- 大规模全自动 WordPress 迁移
- 无审核的自动发布

## 18. 验收标准

MVP 完成时必须能够：

1. 输入一篇自由或结构化 Markdown。
2. 通过自动、半自动或手动模式确定页面生成方向。
3. AI 根据内容选择表达方式并生成完整 HTML 草稿。
4. 草稿通过模板、安全和动态模块校验。
5. 运营人员可视化审核、修改和局部 AI 重写。
6. 页面保存草稿和历史版本。
7. 审核后的页面成功发布到 S3/CDN。
8. 发布失败不影响现有线上版本，并可回滚。
9. 相关产品、产品列表和表单通过 API 加载或提交。
10. 至少完成一组代表性 WordPress 页面迁移验证。
