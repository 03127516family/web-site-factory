# 07 · 发布线与动态能力

## 1. 发布线目标形态

- **部署一条命令**：`npm run deploy` = `check` 全绿 → build → 原子上传 → CDN 刷新 → 打 release tag。
- **回滚一条命令**：`npm run rollback <tag>` = 检出该 tag 的真相层 → 完整重建 → 完整重发。**回滚是"把旧版重新发布一遍"，不是改指针**（原理 6：指针可以指向残缺物，重发不会）。
- **release 模型**：git tag（如 `release-2026-07-15`）= 一次发布的完整快照。不需要数据库发布状态机——git 就是状态机，tag 列表就是发布历史。
- **原子性**：上传采用"先全量上传到位、后切换/刷新"的顺序；任何一步失败，线上保持旧版原样。

## 2. `/zh/` 前缀的架构含义（已拍板 2026-07-02）

生产 URL：`https://www.dgcrane.com/zh/...`——中文站住在**子路径**，为未来英文站（`/en/`）预留。这意味着新静态站要与"根路径上的东西"（现 WordPress 老站，或未来的默认语言站）**共存**，发布拓扑必须支持按路径分流：

- **拓扑 A（推荐）**：CDN/边缘按路径路由——`/zh/*` → 静态托管源（S3/OSS/Pages），其余 → 老站源。切换粒度细，可"新站先上 /zh/ 试运行，老站不动"。
- **拓扑 B**：老站 web 服务器里挂子目录 `zh/`，静态文件直接放进去。最土但零新基建；受制于老站主机的可靠性。
- **拓扑 C**：整站一次性切换到新托管，老 URL 全量 301。动作最大，等新站内容齐了才可选。

推荐路径：**A 起步（/zh/ 先行并存）→ 内容搬齐后视情况 C（老站下线）**。

**构建侧配套——/zh/ 前缀的资源策略**（2026-07-03 审计补，DECISIONS ⑧）：站内链接与资源引用统一相对路径，或构建时注入 base 前缀，二选一钉死；**本地预览必须能模拟 /zh/ 子路径跑一遍**（serve 挂子路径），否则"本地全对、上线全 404"这类前缀事故要到发布日才暴露。此项列入发布线实施的验收项。

## 3. 托管选型决策包（P0-决策，等用户回答 4 问）

## 4. 发布前检查单（deploy 脚本内置，缺一不发）

1. `npm run check` 全绿（测试 + build + geom）；
2. 工作区干净（真相层改动已提交——发布必须对应一个 commit）；
3. sitemap.xml / robots.txt 已随 build 生成（08 章）；
4. 抽查 canonical 与内链均带 `/zh/` 前缀；
5. 上传完成后线上抽 1 页做冒烟（首页/最新改动页 200 + 关键资源可达）；
6. 打 release tag 并推送远端；
7. 安全响应头就位（HSTS、`X-Content-Type-Options` 等，托管层配置）+ HTTPS 强制跳转验证（一次配好，之后每次发布抽查 1 页响应头）。

## 5. 动态能力边界（"80% 静态化"的另一半）

页面主体 100% 静态。全站动态触点白名单（01 章 §2.2）逐项处置：

### 5.1 询盘表单（唯一必须解决的动态点，**方案待拍板、明确暂缓实施**）

**现状**：表单已去重为共享 fragment（`src/fragments/inquiry-form.html`），产品/文章两族字段集已统一（含文件上传）；但它是老站 WPForms 的静态快照，`<form>` 无 action——**现在提交不到任何地方**。footer 订阅表单（`780`）同病。

**候选方案**（拍板时的比较框架）：

| 方案 | 成本 | 数据去向 | 文件上传 | 备注 |
|---|---|---|---|---|
| 第三方表单服务（Formspree/Web3Forms/Tally 类） | 分钟级接入，免费档够询盘量 | 邮箱+服务商后台 | 部分支持 | 最快落地；数据过第三方 |
| 邮件网关（表单→邮件 API） | 半天 | 直达邮箱 | 可做 | 无后台可查历史 |
| 自建（Lambda/云函数 + 存储） | 1–2 天 | 完全自控 | 支持 | **涉 AWS 红线，须用户明示**；用户已说"先别真发，方案以后再说" |

**反垃圾必备**（无论选哪家，2026-07-03 审计补）：honeypot 隐藏字段 + 提交频率限制起步；被垃圾询盘淹没时升级验证码/Turnstile。**询盘数据的归宿**（发到谁的邮箱、哪里能看历史、多久留存）随方案一并拍定——收询盘是这个网站存在的商业目的，此处不许含糊。

**决策纪律**：在用户拍板前，**不接任何真实后端、不建任何云资源**。表单字段集与前端结构已就绪，接哪家都是小改。

### 5.2 站内搜索（可选，触发后建）
pagefind 方案：构建期扫 dist 生成静态索引，前端纯 JS 查询——**仍是静态站，无服务器**。触发条件：内容页 >150 或有"找不到内容"反馈（01 章触发表）。

### 5.3 客服 / AI Bot / 社媒浮窗（可选，触发后建）
第三方 `<script>` 嵌入 chrome（fragments 里加一行）。不自建。外贸站常用的 **WhatsApp / 微信浮动按钮**同此处理——纯前端挂件；号码/账号是站点级值（04 章 §8 `site.md`），运营可点改。

### 5.4 相关产品（**不是动态模块**）
目录站的"相关产品"随目录变化，而目录变化=内容变化=本来就要 rebuild——所以它是**构建期数据**（MD 里的 `related_products`），已静态渲染。旧 spec 把它设计成 API 动态模块是负收益复杂度，已砍（这也是"静态化"原则的一次具体应用：**变化频率等于构建频率的数据，一律构建期定死**）。

### 5.5 动态模块通用协议（预留——真出现"构建期定不死"的数据时启用）

**判据先行**：变化频率 ≤ 构建频率的数据一律构建期定死（如相关产品）；只有真正随时变、且不值得每变一次就 rebuild 的数据（实时库存/价格、行情类）才配走动态。触发（01 章触发表"真实产品数据库"行）后按此协议实现——继承旧 spec §8 的合理部分：

```html
<section data-dynamic="模块类型" data-参数="…">   ← 模版/骨架里的受控占位
  <div data-slot="items"></div>                  ← 数据渲染进 slot
</section>
```

- 全站一份公共 runtime 扫 `data-dynamic` → 请求对应 API → 渲染进 `data-slot`；
- 每类模块必须定义：允许的参数、API 响应结构、**加载态 / 空态 / 失败降级**；
- **铁律：API 挂掉不影响静态主体访问**（模块隐藏或显示降级内容）——动态是点缀、静态是主体，"80% 静态化"里的 80 永远不依赖那 20。
