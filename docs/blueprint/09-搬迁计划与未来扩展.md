# 09 · 搬迁计划与未来扩展

> 前半是 v1.0 的主体工作量：**把老 WordPress 站批量搬进本系统**的方法与完成判据。后半是四项**预留设计**（多语言/搜索/运营自助/多站点）——全部"现在不建"，各带触发条件；预留的意义是保证今天的决定不阻断明天，而不是今天就动手。

---

## 1. 搬迁总策略

**原则**：搬迁 = 逐页执行 SOP（都是 agent 工位的活），不是一次性脚本魔法。AI 烧 MD 这步**需要判断**（哪段是概述/规格/FAQ），自动化脚本只负责搬运原料与盘点清单。

### 1.1 前置条件（先于 B1 批次）

1. 图片闸门生效（08 章 §3）——否则批量搬迁的图要全部返工；
2. SEO 注入就位（08 章 §2）——否则每页要二次过手；
3. `npm run check` 钩子就位（06 章 §2）——批量期最容易忘验证。

### 1.2 盘点（B0）

- **取数通道**：优先 WordPress API/导出（本会话已挂 WordPress MCP 工具，可直接 `wp_list_pages` / `wp_list_posts` / 读 ACF 字段拉原文与元数据）；取不到权限的部分再抓公开 HTML。
- **产出《URL 映射表》**（执行时生成 `docs/blueprint/migration-map.md`）：每行 = 老 URL → 处置（迁入新 slug / 301 到某页 / 有意放弃+理由）。**这张表是搬迁的合同**，完成判据以它为准。
- 顺带盘点：媒体清单（哪些图要过闸门）、老站 SEO 元数据（title/description 可回收进 frontmatter `seo.*`）。

### 1.3 批次划分（依赖顺序，不是重要性顺序）

| 批 | 内容 | 页族 | 前置 |
|---|---|---|---|
| B1 | 产品页（主体量） | product 超集（**就绪**） | 1.1 前置三件 |
| B2 | 文章/案例 | post 骨架族（**就绪**） | 同上 |
| B3 | 分类/品类页 | category（**模版待造**——按 [04 章](04-内容模型与模版契约.md) §4 七步法，这是七步法的试金石） | B1 完成（品类页要链产品） |
| B4 | 首页、联系页、关于页等一次性页面 | 各自新页族（多为骨架型） | B1–B3（首页要链全站） |

**批次门禁**（2026-07-03 补，总表见 [14 章](14-门禁与验收体系.md) G3）：下一批入口 = 上一批的门已过 + 本批前置就位；每批的门 = 该批映射表行全绿（迁入/301/显式放弃三态之一）+ 本批抽样 20% 验收通过。**批内可并行，跨批不许抢跑。**

### 1.4 每页流程与保真分级

- 流程 = SOP-1（产品）/ SOP-2（文章）/ SOP-3（新页族第一页）。
- **保真分级**（别把所有页都当像素级还原做，那是 B1 早期打样的标准）：
  - **像素级**：本页在老站有成熟版式且要求不变 → geom 基准 = 老站快照，逐页 1:1；
  - **族内一致级**（批量期默认）：套现成页族 → geom 基准 = 族内参照页，内容靠人审抽查；
  - **重排级**：老页本来就烂/过时 → 按页族重新表达，人审即可（记录进映射表"重排"）。
- URL：尽量保老 slug；必须改的进映射表 301 列（301 的落地机制随 07 章拓扑定：CDN 规则 / 老站服务器规则 / 托管平台重定向文件）。

### 1.5 验收与完成判据（对应 01 章 v1.0 判据第 1 条）

- 映射表 100% 行行有归宿（迁入/301/显式放弃）；
- 抽样 20%：新旧对照（内容完整性、图、表格、内链、移动端）；
- 全站内链无死链（build 后脚本可查，可并入 check）；
- B3 完成时七步法自检表归档（category 是方法论试金石，它过了，§9 规则即证明页族无关）。

## 2. 预留 ①：多语言（触发 = 用户拍板做英文站）

> **2026-07-03 更新**：多语言的**正式完整设计已移至 [12 章](12-修改传播与多语言同步.md)**（同步状态机、字段级过期检测、人工润色保护、冲突态、hreflang）。本节保留为最初草案；其中"全局 tag（`i18n-en-base`）"机制已被 12 章的 per-page `i18n.source_commit` 取代——按页记录更细、页面各自独立同步。

**已就位的部分**：`/zh/` 子路径（2026-07-02 拍板）——英文站上线时直接住 `/en/`，零迁移。

**预留方案**（触发后照此做，现在不建）：

1. **镜像树**：`src/content/en/<slug>.md` 与中文一一对应；模版共用（marker 不含语言）；`pages[]` 加 locale 维度输出 `/en/`。
2. **字段级增量翻译（关键洞察：git 本身就是增量系统，不需要自建 hash 表）**：
   - 每次英文翻译完成，给中文源打 tag（如 `i18n-en-base`）；
   - 下次同步：`git diff i18n-en-base..HEAD -- src/content/*.md` **直接给出字段级变更**（frontmatter 哪行、哪个 `## 块`变了）——只重译变更处，翻完把 tag 前移。
   - 旧 spec §13 想用 `(data-block-id, data-field)` + hash 表手搓的正是这套东西；MD 真相源下 git 免费提供，且经人工复核的译文不会被"源未变"的机翻覆盖（diff 里根本不出现）。
3. **纪律**：每种语言独立审核发布；hreflang/独立 sitemap 到时随 08 章模式补——同源派生，不漏页。

## 3. 预留 ②：站内搜索（触发 = 内容页 >150 或"找不到内容"反馈）

pagefind：构建期扫 `dist/` 生成静态索引 + 纯前端查询 UI——**无服务器，仍是静态站**，deploy 流程不变（索引就是产物的一部分）。量级 1–2 天。搜索索引永远是派生物，不是页面源数据（继承旧 spec §9.5 正确判断）。

## 4. 预留 ③：运营自助（两级触发，独立演进）

**级 1：托管编辑器**（触发 = 第二个编辑者出现且冲突 ≥1 次，或运营需要远程改值）
把 `npm run edit` 部署到内网/加登录的小主机上，写回走 git 提交（每次保存 = 一个带作者的 commit，审计免费）。加最简单的"页面正在被谁编辑"锁即可，不做角色权限——真相仍在 git，编辑器仍只是窗口。

**级 2：建页薄壳**（触发 = 月建页 >8 且"等 agent 会话"成瓶颈）
用 Agent SDK 包一个最小入口：运营贴文章+产品名+slug → 后台起 agent 跑 SOP-1/2 全流程 → 回预览链接 → 运营确认 → 进待发布。**壳是薄的**：它只是把"用户在 Claude Code 里说三件事"变成一个表单，管线、验证、纪律全部复用，不新增任何真相源。

## 5. 预留 ④：多站点（触发 = 真出现第二个站）

引擎与 marker 词汇表天然站点无关（零名字逻辑的红利）；届时仓库级复制或 monorepo 拆 `sites/<name>/src`，共享 `scripts/`。一句话记到这，不展开。

## 6. 预留的总纪律

预留 = **文档里的方案 + 今天不阻断它的最小结构决定**（如 `/zh/` 前缀、marker 无语言、git 真相源），**不是**今天写代码。谁想提前实现，请出示 01 章触发表命中证据；出示不了，就是范围爬行。
