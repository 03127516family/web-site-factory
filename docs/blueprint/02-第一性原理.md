# 02 · 第一性原理：系统为什么长这样

> 本章是给"未来接手的人或 AI"的：每条承重规则的**推导过程**，而不只是规则本身。规则可以背，但只有懂推导才不会在新场景里做出违反初衷的决定。最后附一节案例复盘——本项目最重要的一次决策反转，以及从中提炼的方法论。

---

## 原理 0：访问态 ≠ 真相态

- **访问态**：访客浏览器拿到的东西。本系统永远是"预先生成好的静态 HTML，CDN/静态托管直出"——这一点与任何方案无关，是不变量。
- **真相态**：后台修改、重新发布时**依据**的东西。全部争论只发生在这一层。

界定 WordPress 的从来不是"有没有结构化数据"，而是"**每次访问都在活服务器上现拼 HTML**"。Hugo/Astro 全是"结构化数据→HTML"，没人说它们是 WordPress——因为转换发生在构建期，访客拿死文件。（此澄清继承自 2026-06-22 纪要 §2/§3，是那份纪要里至今有效的部分。）

## 原理 1：真相源必须能确定性地推导出页面

**需求**：页面在生命周期里必然被"再生成"——模版改一处、字段加一个、全族重渲、未来翻译、审计回放。所以必须存在一个确定函数 `f(真相源) → 页面`，且真相源要经得起编辑与版本管理。

**候选淘汰赛**：

| 候选 | `f` 存在吗 | 编辑写回 | 版本/审计 | 判定 |
|---|---|---|---|---|
| 裸文章（散文） | `f` = AI，每次输出都不同，不确定 | 无处写 | 可进 git | ✗ 只能当**原料** |
| 成品 HTML | **不存在 `f`**——页面自己就是真相，无法再生成；改模版=挨个改 N 份拷贝 | 写回=改 HTML，配套的 markdown 第一次编辑后即过期 | diff 噪声大（内容与版式焊死） | ✗ 旧 spec 路线，已被实践反转（见文末案例） |
| **结构化 MD（现行）** | `f` = `render.mjs`，确定、免费、可批量 | 编辑器按坐标定点写回 | git diff 即**字段级**差异；人可直读 | ✓ |
| DB 里的 blocks(JSON) | 同样确定 | 可 | 要自建版本表；人不可直读；多养一个服务 | ✗ 单人静态站不回本（翻案条件见 01 章触发表） |

**推论**：
- 裸文章 → MD 这一步有信息增益（判断哪段是概述/规格/FAQ），**必须有人或 AI 做判断**；MD → HTML 零信息增益，**必须是代码**。
- "上下文是耗材，MD 是资产"：能脱离对话上下文还原页面的是 MD。任何只存在于对话里的结构决定都是负债，必须落盘。

## 原理 2：AI 用在判断处，代码用在重复处

成本与确定性的双重约束：

| | 创作（烧 MD / 造模版） | 装配（MD → HTML） |
|---|---|---|
| 发生频率 | 每页 1 次 / 每页族 1 次 | **每次 build**（天天发生） |
| 本质 | 语义判断（这段是什么、该进哪个槽） | 机械替换、克隆、裁剪 |
| 分给谁 | AI | 代码 |
| 如果弄反 | 代码里写死判断 → 引擎长满 `if`，页族数 N 增长引擎复杂度 O(N)，烂掉 | AI 每次 build 介入 → 贵、慢、输出漂移、不可复现、不可验证 |

一句话铁律：**AI 只出现在写入时（write-time），永不出现在渲染时（render-time）。**

这也解释了系统"是什么形式"：它不是"后端调大模型的服务"（那是把 AI 放进 render-time），也不是纯人肉 CMS（那是把判断留给最贵的人力）。AI 以 **agent** 形态出现在创作工位——因为创作是一个带修正回路的过程（烧 MD → build → verify → 不对再改），需要工具调用与迭代，一次性 API 调用没有回路。

## 原理 3：结构自声明，引擎零知识

**规则**（CLAUDE.md §2 铁律的原理层）：引擎永远只有一个，不认任何具体名字；模版用 marker（`data-field` / `data-repeat` / `data-optional` / `data-array` / `data-edit`）自己声明结构；引擎的全部判断只许依据 **marker + 内容形态**。

**为什么**——复杂度归纳：

- 若引擎认名字（"single-girder 的规格表这样渲"）：每加一个页族/字段都要动引擎，引擎复杂度 O(页族数)，每次改动都可能回归到所有旧页面。这正是 WordPress 主题函数堆积的死法。
- 若结构自声明：引擎复杂度 **O(1)**。新页族 = 新增一份模版文件（AI 烧一次），引擎零改动，旧页面零风险。

**实证**：posts 页族接入时引擎零改动（2026-06-29 方案落地）；现库 7 页、2 个页族、1 个引擎。归纳成立。

**推论（对造模版的人/AI 同样生效）**：CLAUDE.md §9 说"造模版的人也不认页族、只按内容形态挂 marker"——因为任何"某页族要特殊切法"的想法，等于把 O(N) 逻辑从引擎挪进人脑，同样烂，只是烂得慢一点。

## 原理 4：可编辑性的物理条件（三级编辑模型的由来）

屏幕上一个点**能被就地编辑**，当且仅当同时满足三个条件：

1. **坐标**：这个点知道自己来自 MD 的哪里。实现：渲染时 `buildData` 在"字段实际取自哪"**就地登记**写回坐标（取自 frontmatter → `fm:`，取自 `## 块` → `mdhead:` / `mdbody:`）。读哪写哪，坐标表与数据同源，不存在第二张要人工维护的映射表——对称性是防漂移的关键。
2. **类型**：`data-edit="text|rich|image|link"` 决定编辑控件和序列化方式。
3. **互逆**：富文本要求 `htmlToMd` 与 `mdToHtml` 互为逆变换（含 `<table>` ↔ 管道表格）。往返一次不能有损，否则每次保存都在腐蚀内容。

**推论 1（互斥定律）**：自由 HTML 没有坐标 → 不可编辑。"可见即可编辑" ⊕ "任意自由排版" 二者不可兼得——这不是产品取舍，是定律。
**推论 2（两全解）**：把**版式**冻进骨架（模版，L3），把**值**留在 MD（L1）——骨架带坐标槽，值就地可编辑，版式因为不可编辑所以永不烂。posts 页族"每篇一份骨架模版"就是这个解——它同时回收了旧 spec 想要的"AI 自由排版每一页"。
**推论 3**：这就是 01 章三级编辑模型（值/结构/版式）的物理来源。

## 原理 5：验证分层，失败即中止，绝不静默降级

| 层 | 工具 | 保什么 | 不保什么 |
|---|---|---|---|
| MD 合法 | `validateBlocks`（build/verify 共用） | 每个 `## 块`带合法 `<!--block:KEY-->` 且 KEY 在模版有着落 | 内容对不对 |
| 装配成功 | `npm run build` | 模版+MD 能出 HTML | 版式对不对 |
| 版式无损 | `npm run verify:geom`（逐元素几何比对） | 与基准 1:1，版面没塌 | 文案对不对 |
| 内容正确 | 人工预览 | 事实、语义、图文对应 | — |

**设计要求**：每层失败必须**中止并报出具体位置**。`validateBlocks` 的诞生就是教训：编辑器扩展把 `<!--block:KEY-->` 改写成链接，正文整段悄悄失效而 build 照样通过——"改坏不报错"比"改坏"危险一个数量级。防线永远做在编辑器无关的校验层，编辑器配置（关 formatOnSave）只是辅助。

**边界诚实**：`verify:geom` 证明的是"几何 1:1"，不证明内容正确——所以人工预览这一层不可省，AI 永远只出草稿、人是发布闸门（红线，见 01 章非目标表）。

## 原理 6：发布是原子交换

线上永远不存在"半新半旧"状态。发布 = 完整产物整体切换；任一步失败 → 线上保持旧版原样；回滚 = **把旧版重新完整发布一遍**，而不是改一个指针（指针可以指向已残缺的东西，重发不会）。此原则继承自旧 spec §11（它写对了的部分），实现落在 git tag + 幂等部署上（07 章），不需要数据库状态机——git 本身就是状态机。

## 原理 7：行为是权威，文档会漂移

`product.contract.md` 已经漂移过一次，教训固化为权威顺序（README §3）：**代码行为 > CLAUDE.md 决策日志 > 蓝图 > 历史文档**。长期方向是让文档尽量**派生**（如从模版 marker 生成字段契约，P2），手写文档只写"为什么"（原理、决策），少写"是什么"（是什么让代码自己说）。

## 案例复盘：真相源决策的 24 小时反转

系统史上最重要的一次转折，值得完整记录——**它决定了整个系统的形状，而且它的教训比结论更值钱。**

**时间线**：

- **06-19**：spec 写成——HTML 当真相源，AI 直出成品 HTML，Postgres 存草稿版本。
- **06-22**：正式拍板（专门的决策纪要）：走 HTML 真相源；"blocks 方案"（结构化真相源+确定性渲染器）保留不实现，理由是"渲染器是回不了本的前期税"；纪要里特意写了"避免日后翻案"。
- **06-23**：做第二个页面（overhead）时，"渲染器路线"胜出。
- **06-24 至今**：确定性渲染器 + marker 模版 + 双向编辑器 + verify:geom 全面建成——**恰好是被否决的那条路线**，只是 blocks 的载体从"数据库 JSON"换成了"git 里的 Markdown"。7 页、2 页族、全部 1:1，编辑 round-trip 成立。

**06-22 的分析错在哪**（不是立场错，是建模错）：

它只问了"blocks 的回本场景**存不存在**"——全站换皮？本站不换。多语言？远期。于是判定不回本。它没有按"**事件频率 × 单次成本**"建模，漏了两个高频项：

1. **同族第 N 页的生产成本**。HTML 真相源下，每加一个产品页 = AI 重新生成一整页不可复现的 HTML + 全页人审；渲染器路线下 = 只写一份 MD。而"把老站几十页搬进来"正是本项目的主体工作量——**回本点不在上线后，而在搬迁期**。
2. **建设期的全族重渲**。模版每改一处、字段每加一个，都要全族重出 + geom 重验——这两周里天天发生。"重新生成"不是罕见事件，是日常。

**方法论教训（三条，供未来一切架构决策使用）**：

1. **按"频率 × 成本"建模，不按"场景是否存在"清点。** 低频大事件容易被高估，高频小事件容易被漏计。
2. **"避免日后翻案"这句话防不住翻案。** 正确的防翻案写法是把决策**前提**写成可检验断言（例："本决策成立当且仅当同族页面 ≤ 2 且无批量搬迁"）——前提一破，决策自动失效，不需要谁没面子。本蓝图各章的"翻案条件/触发表"就是这个写法的落地。
3. **第 2 个实例比第 10 轮讨论信息量大。** 反转不是开会开出来的，是做 overhead 页时撞出来的。架构存疑时，最便宜的实验就是尽早做第二个实例。

**同时要诚实继承**：06-22 纪要的分析框架本身是好的（访问态≠真相态、WP 的界定、blocks 收益清单）——把漏掉的变量补进它自己的框架，结论就自动反转了。错的不是框架，是输入不全。这也是留着那份纪要、只加追记不删除的原因：**决策历史是资产，包括错的那部分。**
