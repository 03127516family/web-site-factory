# 00 · 系统总流程（主轴）——从一份 MD 到多语言托管站的完整链路

> **这份是主轴**，其余 01–15 章是它每一段的放大。用户 2026-07-03 定调：要的不是散章，是"一条流程从 MD 到 HTML、到 SEO、到多语言、到发布、到访问、到别人改、到同步其他语言、到管理"贯通的系统。本章按这个顺序走一遍，每段给**具体**机制（S3 路径 / Lambda / 数据流），不推给"未来"。

## 系统身份（一句话钉死）

> **用 AI 操作、以 Markdown 为真相、代码与 AI 都能把 MD 组装成 HTML、产出静态站、发到 S3/CloudFront、少量动态走 Lambda、支持多站点多语言、运营在浏览器里可见即可编辑——用来取代 WordPress。**

五条不可动摇的属性：① 取代 WordPress（无 PHP、无 MySQL、无活服务器渲染）；② **抛弃 Python**（预览/验证的 `python3 -m http.server` 换成 Node 静态服务，全栈 Node+云）；③ 静态优先，动态少而白名单化；④ AI 是操作者（创作、翻译、装配都可由 agent 干）；⑤ 多站点 × 多语言从数据模型第一天就不阻断。

## ① 原料 → MD 真相（烧制）

- 输入：裸文章 / 旧 WordPress 页 / 产品资料。放 `sites/<site>/content/<lang>/raw/`。
- 动作：**AI agent 判断归类**（哪段是概述/规格/FAQ…）→ 写结构化 MD。这步需要语义判断，是 AI 的活，不是脚本。
- 产物：`sites/<site>/content/<lang>/<slug>.md`——**一份 MD = 一个页面**，frontmatter 顶部带 `page:` 登记块（slug/type/lang/title/description/template + 可选 mode/geomBaseline/family）。**登记即内容，系统不存在第二个登记处**（这是 F1 收敛已落地的地基，见 15 章）。
- 真相载体：**git**。版本、diff、作者、审计全是 git 原生能力，不建数据库当真相。

## ② MD → HTML（两条组装路，都产出"带 marker 的 HTML"）

用户硬要求：**AI 能组装，代码也能组装**。两条路并存，输出同构，所以后面 ③④⑤⑥ 不关心是谁组的：

| 路 | 组装器 | 什么时候用 | 产物 |
|---|---|---|---|
| **A 引擎路（默认）** | `render.mjs`（纯代码，确定性）：读模版 marker，把 MD 填进去 | 所有标准页；批量；每次 build 免费可复现 | HTML |
| **B AI 路** | agent 直接按 MD + 目标风格写 HTML / 设计新骨架模版 | 新页族第一次、引擎 marker 表达不了的一次性特殊版式 | HTML |

**两路的铁律**：无论谁组，产物都必须带同一套 marker（`data-field`/`data-repeat`/`data-optional`/`data-edit`）——因为 marker 是⑥编辑器认坐标、③SEO 取值、以及"引擎日后接管 AI 页"的共同接口。B 路产出后同样过 `validateBlocks` + 几何校验才算数。**AI 组的页也能被引擎重渲、被编辑器编辑**，就是靠这条。

> 现状：引擎路 7 页跑通、1:1；AI 路封存但能力保留（每篇 post 一份骨架就是 AI 设计的版式）。本设计把 B 路正式恢复为"新页族/特殊版式"的合法组装器，不再是逃生舱。

## ③ SEO（从 MD 自动派生，已实现 L1）

- 组装完 HTML 后，`{{SEO}}` 占位符被 `seoHead(page, fm)` 填满：canonical、OG 全套、JSON-LD（product→Product / post→Article，都带 BreadcrumbList）、`og:locale`。全部**从该页 MD 同源派生**，不手写。
- `sitemap.xml` 遍历登记生成（同源不漏页），lastmod = 该 MD 的 git 提交日期。
- 责任分层（08 章）：L1 技术标签=代码自动；L2 页面语义（标题/描述/alt/内链）=烧 MD 时 AI 顺手做；L3 关键词→页面映射=AI 调研起草；L4 外链=不做。
- 多语言 SEO：每语言独立 canonical/sitemap，hreflang 成对生成 + x-default，语言切换器与 hreflang 同源（12 章 §3.7）。

## ④ 多语言（镜像树 + 字段级增量，见 ⑦ 的同步动作）

- 数据模型：`content/zh/<slug>.md` ↔ `content/en/<slug>.md` 路径镜像即逻辑配对；模版跨语言共享（marker 不含语言）；每语言一份 `page:` 登记，`pages[] × lang` 输出 `/zh /en`。
- 目标语言 MD 也是真相、也可被⑥编辑。多语言的"改了怎么同步"是 ⑦。

## ④→发布：发布到哪（S3 存储设计，具体桶与路径）

**三个 S3 平面 + git，各存各的，互不混淆：**

```
git（源真相，版本/审计）
  sites/<site>/content/<lang>/*.md      内容
  sites/<site>/templates/*.html         模版
  sites/<site>/fragments/*.html         chrome
  engine/                               render.mjs 等（跨站共享、版本化）

s3://sf-drafts/                         草稿平面（编辑中、未发布）
  <site>/<lang>/<slug>.md               ⑥的实时保存落这

s3://sf-web/                            发布平面（CloudFront 源，访客拿的）
  <site>/<lang>/index.html
  <site>/<lang>/products/<slug>/index.html
  <site>/<lang>/posts/<slug>/index.html
  <site>/<lang>/sitemap.xml
  <site>/assets/{css,js,img,files}      本地化静态资源

s3://sf-media/                          媒体（运营上传的图/PDF，压缩后）
  <site>/img/... <site>/files/...
```

**发布动作 = `publish` Lambda**：读冻结的 MD → 引擎渲染 → 写 `sf-web` 临时前缀 → 校验 → 切正式路径 → CloudFront 失效刷新 → 打 git release tag。**原子**：任一步失败，线上保持旧版；**回滚 = 重发上一个 tag**（不是改指针）。

**为什么发布产物不进 git**（回应你早前的话"网站肯定不在 git 里"）：git 存"菜谱"（MD/模版），S3 存"做好的菜"（HTML）。菜丢了照菜谱一键重做，所以菜不必进 git。

## ⑤ 访问（访客侧，纯静态 + 少量动态）

- 访客 → CloudFront → `sf-web` 的静态 HTML。**无服务器渲染、无 PHP、无数据库**——这就是取代 WordPress 的核心红利（攻击面≈0、快、便宜）。
- `/zh/` 子路径与老站/未来英文站按 CloudFront 多源路由共存（`/zh/*`→S3，其余→老站，逐步切换）。
- **动态少量、白名单**：询盘表单 POST → `form-submit` Lambda → Postmark 发邮件（现阶段 mock，端点单常量，切真改一行）；可选站内搜索=构建期静态索引（pagefind，仍无服务器）；可选客服=第三方脚本。**动态挂了不影响静态主体访问**。

## ⑥ 他人修改（可见即可编辑——云端产品形态，端到端往返）

这是你反复强调、我之前只做了本地版的。云端往返：

```
运营浏览器
  1. 管理软件里点某页 →「编辑」
  2. 载入编辑器：iframe 里渲染该页的"带 marker 版"+ editor.js
  3. 鼠标点某处 → editor.js 按 marker 算出 MD 坐标(fm:/mdbody:...) + 值
  4. POST {site,lang,slug,坐标,类型,值} → API Gateway
        ▼
  edit-save (Lambda)
  5. 取当前 MD(草稿/ git) → patchMarkdown 定点改写(现成纯函数) → 写 sf-drafts
  6. render.mjs 重渲该页 → 预览 URL 返回
        ▼
  7. 运营看到预览即所改；满意 →「发布」→ publish Lambda(见④)
```

**关键**：`editor.js` / `patchMarkdown` / `render.mjs` 是**现有本地内核里的纯函数，被 Lambda 原样当载荷复用**——本地那套不是玩具，是云端引擎本体。可编辑范围仍是三级模型：值(L1 点改)、结构(L2 改 MD)、版式(L3 走模版，不在后台改)。

## ⑦ 同步修改到其他语言（改了中文，英文怎么办）

```
中文某页发布后
  → i18n-diff (Lambda)：git 取该页译文对应的 source_commit 版 vs 当前版，
     解析成结构做字段级比对 → 输出"变更字段清单"(hero.title / overview 块 / ...)
  → 目标语言该页标"已过期：3 处"，显示在⑧管理软件的 i18n 面板
  → translate (Lambda)：AI 只重译清单里变更的字段(其余不碰)→ 写目标语言草稿
  → 人审(双语) → 各语言独立发布(④)
```

**人工润色保护**：任务只碰"源变了的字段"，英文侧手改过、而中文源没变的字段——永不被机翻覆盖（机制保证）；源变且目标被人改过→标"冲突待人工"。换版式全语言零翻译成本（模版共享）。详见 12 章。

## ⑧ 管理（管理软件设计）

**形态**：静态 SPA（挂 `sf-web` 的 admin 子域 + CloudFront）+ API Gateway + Lambda + 元数据小库。**后台全挂，线上站照常访问**（后台不在访客链路上）。

| 组件 | 选型 | 存什么/干什么 |
|---|---|---|
| 前端 | React SPA（静态托管） | 站点列表 / 页面列表 / 可视编辑器 / 新建页 / 发布回滚 / 媒体库 / i18n 面板 |
| 认证 | Cognito | 角色：编辑者/发布者/管理员；AI 永远只出草稿、发布必经人 |
| API | API Gateway + Lambda | 下方清单 |
| 元数据 | DynamoDB | **非真相**：任务状态/页面锁/发布历史缓存/用户。页面列表**从 content 目录派生**（呼应 F1，真相仍 git） |

**页面状态机**（= git 的投影，不需另建）：草稿(sf-drafts 有)→预览就绪→待发布→已发布(git tag)。审计=commit 历史+任务日志。

## Lambda 清单（整套后端就这几个函数，各一件事）

| Lambda | 输入 → 输出 | 复用的内核 | 权限边界 |
|---|---|---|---|
| `render-page` | (site,lang,slug)→HTML | render.mjs | 只读源 |
| `edit-save` | (坐标,值)→草稿+预览URL | patchMarkdown+render.mjs | 写 sf-drafts |
| `publish` | (site,lang,slug\|all)→S3+CF+tag | render.mjs | 写 sf-web+CF失效+git tag |
| `rollback` | (site,tag)→重发 | render.mjs | 同上 |
| `generate` | (原料,名,slug,模式)→草稿MD(+骨架) | AI agent(§②烧制) | 写 sf-drafts/草稿分支 |
| `media-ingest` | 上传→压缩→路径 | sharp(Node) | 写 sf-media |
| `form-submit` | 表单→邮件 | Postmark | 公开端点，仅发信 |
| `i18n-diff` | (site,slug)→变更字段清单 | 结构 diff(纯代码) | 只读源 |
| `translate` | (slug,目标语言,清单)→目标草稿 | AI agent | 写 sf-drafts |

## 现有本地内核如何原样变成云端引擎（不重写，只打包）

| 本地纯函数 | 云端角色 |
|---|---|
| `render.mjs` | `render-page`/`publish`/`rollback` 的载荷 |
| `patchMarkdown`(md-write) | `edit-save` 的载荷 |
| `editor.js` | 直接跑在浏览器 iframe 里（本就前端） |
| `validateBlocks`/`verify-geom` | CI 质量门 + publish 前校验 |
| `build.mjs::loadPages` | 页面列表 API 的实现 |

**这就是当初坚持"引擎是纯函数、零名字逻辑"的全部回报**：本地怎么跑，云端就怎么跑，一行不用重写。
