# 11 · 产品化架构

> 服务于 [10 章](10-产品化形态与路线.md)路线图的技术方案：组件、选型判据、关键论证、演化路径、开放问题。总原则：**内核不动（`scripts/` 原样就是引擎），产品是包住内核的壳；壳的任何部分坏掉，都不影响线上静态站，也不丢真相。**

---

## 1. 总架构图（M2 完成态）

## 2. 组件清单与选型判据

### 2.1 真相层：托管 git（每站一仓库）

- 内容仓库 = `src/content` + `src/templates` + `src/fragments` + `public/assets`（即现仓库的真相部分）。
- 选型判据（DECISIONS 待拍板 #3）：私有仓库、API 完善（后端要程序化读写/commit）、团队网络可达稳定。候选：GitHub（生态最全）/ Gitee（国内快）/ 自托管 Gitea（最自主，多一台运维）。
- **为什么真相仍不进数据库**（02 章原理 1 的产品化重申）：版本、diff、作者、审计、字段级增量（含未来翻译，09 章 §2）全是 git 原生能力；DB 当真相要自建这一切且人不可直读。产品只允许一个**运营小库**（SQLite 起步）存账号/会话/任务状态/页面锁——全部可丢弃，重建不伤内容。

### 2.2 应用服务（一个小 Node 后端，M2）

- 内容 API：读 MD / 写 MD（写 = commit + push，作者 = 登录用户）。
- 任务编排：生成/构建/发布/回滚四种任务的创建、排队、状态、日志。
- 认证与角色、页面级软锁。
- 规模纪律：单实例 + SQLite 起步。**刻意保持在"一个人一个周末能重建"的量级，超过这个量级的设计一律砍**——这是 01 章"单人可运维"在产品期的延续。

### 2.3 托管编辑器（M1 就要，产品最早露头的部分）

- `editor.js` 与坐标系统（`fm:/mdhead:/mdbody:`、patchMarkdown）**零改动**——内核当初就是按可移植设计的。
- `edit-server` 加三件事：登录、保存 = commit（替代裸写盘）、页面锁查询。
- 部署形态：内网小服务器，或加认证的公网小实例；HTTPS 必须。
- 媒体上传（2026-07-03 完整性审计补）：编辑器改图时允许直接上传新图——服务端自动过图片闸门（压缩+尺寸校验+补宽高，SOP-6 的产品化）后落 `public/assets/img/` 并随保存一起 commit；运营从此不手工处理图片。
- 粘贴清洗（同上审计补）：运营常从 Word/微信粘贴——粘贴内容一律经 `htmlToMd` 归一化（只保留段落/加粗/列表/表格等 MD 能表达的结构，样式垃圾全部丢弃），保证真相层永远干净。
- 附件上传（外贸站审计补）：PDF 目录/规格书与图片同一入口上传，过附件规范（08 章 §3）落 `assets/files/` 并 commit。
- **页面历史与一键回退**：每次保存=commit 的直接红利——后台每页有"历史"视图（谁、何时、改了哪些字段）与"回退到此版"按钮（= revert 该页 MD 后重渲）。运营敢放心改，是"可见即可编辑"敢交给非技术人员的底气。

### 2.4 生成 worker（M2 核心）

- **形态：Claude Agent SDK 无头 agent 任务，不是裸 completion 调用。** 理由（02 章原理 2 + 原型实证）：烧 MD 是带修正回路的工作（烧 → validateBlocks → build → geom → 修，直到过），一次性补全没有回路，质量不可控。原型期"我在 Claude Code 里干的活"，产品期由同类 agent 在服务器上干，**干的活和守的规矩一字不变**（CLAUDE.md/蓝图就是它的系统提示素材）。
- 任务流：领取 job（原料 + 页族 + 模式参数）→ 隔离工作区 checkout 草稿分支 `draft/<slug>` → 烧 MD（post 则 + 骨架模版）→ 跑内核自检（validate + build + geom vs 族基准）≤N 轮自修 → push 分支 → 触发预览构建 → 回报（预览 URL + 生成报告：段落归属、缺图清单、没把握之处）。
- 三种模式 = 同一条任务流的提示与约束参数（自动/半自动/手动，旧 spec §5.2 在此复活）。
- **边界与安全**：worker 只持有内容仓库 `draft/*` 分支的写权限；无任何云基础设施权限（AWS 红线的产品化版本）；单任务 token 预算上限 + 自修轮次上限；失败保留分支供带反馈重试，**永不触碰 main 与线上**（回收旧 spec §15：不覆盖可用版本）。
- **质量管理——把 AI 当成要养的组件，不是魔法**（2026-07-03 审计补，DECISIONS ⑤）：
  ① **缺料不造料红线**：原料里没有的关键事实（参数/数字/型号/认证）一律不许编造——缺图走 known-leftover，缺文案在生成报告标"待补料"（继承旧 spec §5.3"内容不足必须提示"）；
  ② **生成回归集（golden set）**：固定 2–3 篇已知原料 + 期望 MD 结构，**每次换模型、改提示词、改知识包必跑**，比对字段归属与结构差异——AI 行为漂移要像代码回归一样被拦住；
  ③ **知识包版本化**：生成 worker 的提示素材（烧 MD 规则、页族契约、活样例）从蓝图/契约派生，随引擎一起版本化发布，不许散落在任务配置里；
  ④ **质量反馈环**：以"人工修正率"（生成后被人改动的字段占比）为月度质量指标，高频修正模式回流进知识包与规则；同一份月报带 **token 成本汇总**（每页生成成本可见，异常任务可追）。

### 2.5 构建 / 发布 worker（M1 起步于 CI，M2 并入任务系统）

- 容器镜像：node + chromium（geom 需要）；跑的就是 `scripts/` 内核命令——**worker 没有自己的渲染逻辑**。
- 预览：draft 分支 → 构建 → 预览路径（独立 bucket/路径 + noindex + 简单访问控制）。
- 发布：merge 到 main → `check` 全绿 → 构建 → 原子上传（先传后切）→ CDN 刷新 → 打 release tag。回滚 = 检出旧 tag 完整重发（[07 章](07-发布线与动态能力.md)模型原样上云）。

### 2.6 页面状态机（回收旧 spec §10，但状态 = git 的投影）

```
草稿（draft/<slug> 分支存在）
  → 预览就绪（该分支预览构建绿）
  → 待发布（编辑者提交，等发布者）
  → 已发布（merge + release tag）
失败态只存在于任务记录，不存在于内容。
```

**状态不需要真相级存储**——分支/合并/标签就是状态机，运营小库只缓存展示用副本。审计 = commit 历史 + 任务日志。这是"git 当数据库"的最后一块拼图：旧 spec 的 page/version/publish_job 三张表，分别被 分支/commit/tag+任务日志 原生替代。

## 3. 动态 API 边界

维持 07 章 §5：表单端点是独立小函数/第三方，与应用服务解耦。**访客链路只依赖 对象存储+CDN（+表单端点）**；应用服务、worker、托管 git 全挂，线上站照常访问——静态架构的核心红利，产品化不得破坏（10 章 §7 防漂移清单第 5 条）。

## 4. 安全

- 后台：HTTPS、登录、角色、页面锁；编辑器公网暴露必须有认证层。
- 密钥：LLM API key、仓库 token、部署凭证全在服务端 secret——永不进仓库、永不进浏览器。
- 权限最小化：生成 worker 只能写 `draft/*`；构建 worker 只读内容仓库；发布 worker 只有产物桶写权限 + tag 权限。
- 内容安全：内核 validateBlocks + 产物零 `data-*` 照旧；编辑器保存走 `htmlToMd` 序列化路径，值里不存在任意 HTML 注入面；生成物合并前必过人审（红线）。

## 5. 成本与运维素描（团队级）

1 台小服务器/容器（应用 + 编辑器 + worker 同机起步）＋ 对象存储/CDN（近乎忽略）＋ 托管 git（免费档）＋ LLM token（每次建页一次性消耗，任务级预算上限）。没有必须 24×7 盯的东西——后台宕机不影响线上。

## 6. 从现仓库到产品的演化路径（不推倒重来）

| 里程碑 | 仓库动作 | 备注 |
|---|---|---|
| M1 | 现仓库加 remote；CI 配置进仓库；`edit-server` 加认证小改；deploy/rollback 脚本进 `scripts/` | 仓库结构不变 |
| M2 | 新建 `app/`（或独立应用仓库）放应用服务与 worker；**`scripts/` 保持可独立运行**——本机形态永久保留，它是产品的调试态与逃生舱 | dgcrane 内容留在本仓库（第一站） |
| M3（若多站） | `scripts/` 抽成版本化引擎包；每站一内容仓库、显式引用引擎版本；引擎升级 = 逐站跑 geom 回归 | "引擎只有一个"原理的多站投影 |

## 7. 多站点模型（M3 概述，等 DECISIONS #4 拍板后细化）

"每一个网站如何管理"的答案 = **站点注册表**：后台维护 N 个站点条目，每站独立一套内容资产，共享同一套引擎与后台。

| 每站独立（互不影响） | 全局共享（只有一份） |
|---|---|
| 内容仓库（content / templates / fragments / assets / `site.md`） | 引擎（`scripts/` 版本化包；按站锁版本、显式升级） |
| 发布目标（域名/路径/托管/CDN）与 release 历史 | 后台应用与 worker 池 |
| 语言集与 i18n 同步状态 | 账号体系（按人对站点授权） |
| geom 基线、生成 golden set | 质量门规则与图片/附件闸门 |

- **站点间零耦合**：一站的改动/发布/回滚物理上不可能影响另一站（仓库隔离）。
- 引擎升级 = 逐站跑 geom 回归、逐站切版本——"引擎只有一个"原理的多站投影：代码只有一份，版本按站推进。
- 对外产品形态（租户/配额/计费）不在此预设计，等 DECISIONS #4 拍板。
